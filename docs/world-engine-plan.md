# Neno 世界引擎规划

日期：2026-09-25。状态：独立后端已实现并通过临时数据库场景验证；当前聊天服务未启用世界模块。实施范围见第 14 节及 world-backend.md。

本轮不恢复旧 consciousness 模块，不重启服务，不恢复人设提示词，不改变 TG 发送策略。

## 1. 核心目标

世界可以是虚构的，但状态、时间和后果必须持续存在。

目标不是给聊天模型补一大段“她今天干了什么”的提示词，而是建立一个独立于 Neno 及聊天、能持续推进的世界：世界有自己的时间、环境、场所、资源和 NPC；Neno 是其中一个参与者。她的活动可以影响世界，但不是世界运行、事件生成或其他角色行动的前提。只有她可感知或有权查询、且与当前情境相关的内容进入聊天上下文。

体验上的结果：你不聊天时事情也会继续；你回来时她不是重新生成一段人生；她能改变计划，也会遇到约束；世界变化不等于每次聊天都要播报生活。

旧稿可借鉴“规则底盘 + 稀疏模型决策”，不继承固定八秒循环、每天成本承诺、几十个心理属性模块和旧人格设定。

## 2. 三层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 世界底盘 | 时钟、实体、行动持续时间、事件、资源变化、约束、任务恢复 | 写聊天台词、不断调用模型 |
| 角色决策 | 根据目标、认知和新事件提出意图、调整计划、解释重要经历 | 任意覆盖整个数据库、把愿望当作已发生事实 |
| 聊天表达 | 读取当前世界中与对话有关的部分，自然回应，必要时执行工具 | 临时捏造已经发生的经历、每句播报后台状态 |

世界事实、角色认知、聊天表达不是同一份数据。

- 世界事实：已经提交的事件及其结果。
- 角色认知：她知道或相信什么，可以不完整，也可以被新证据修正。
- 对外表达：她此刻选择说什么，不要求把世界内容全部告诉用户。
- 身份、人设与世界设定分开配置；开发阶段继续关闭人设提示词。

## 3. 世界中保存什么

规划一个有明确模拟边界、但独立于 Neno 的持续世界，支持 NPC、场所、物品和关系。已纳入的区域不会因为 Neno 不在就停止；世界边界控制实现规模，不按 Neno 当前注意力决定事实是否存在。

核心对象：

- 世界：world_id、时间、时区、暂停状态、版本号、初始设定。
- 实体：人物、地点、物品；保持稳定 ID，不每轮重新生成。
- 行动：意图、参与者、目标、开始与预计结束时间、前提、执行状态、结果。
- 目标：长期关注、近期计划、对用户的承诺，以及阻碍目标的未解决事项。
- 关系：角色之间已经发生的互动及其影响，不先压成一个万能好感度分数。
- 事件：发生时间、原因、来源、参与者、状态变化、关联消息或图片 ID。

对活动、情绪或身体状态，只加入确实会影响选择的维度，不为了“像真人”堆数值。无需把每个状态变量拆成独立引擎。

必须区分信息来源：模拟世界事件、用户陈述、图片观察、角色推测。用户说过某件事不等于系统独立核实过；模型推测也不能直接成为世界事实。

初始设定作为独立 world seed。不能从已删除的旧人设里偷偷恢复学校、年龄、职业或既有人际关系。

## 4. 如何推进

### 4.1 时钟推进状态，事件触发决定

普通变化由代码处理：活动到期、移动完成、约定到时、资源消耗、长时间未处理事项。运行器可以轻量检查到期任务，但检查本身不等于调用 LLM。

角色决策只在有意义的边界触发，例如：

- 当前行动完成，需要选择下一步。
- 用户提出邀请、做出约定，或者带来会改变计划的信息。
- 已有计划遇到真实阻碍，继续执行已不成立。
- NPC 的行动带来相关后果。
- 长期目标持续未推进，需要重新安排，而不是机械地每分钟“思考一次”。

同一时间的一组事件合并处理。非紧急决策受冷却时间和调用预算约束；额度耗尽时已有计划和规则仍能运行。

### 4.2 意图不是已完成行动

流程：事件发生 → 读取相关状态 → 模型提出意图 → 检查前提 → 安排行动或提交结果 → 写入事件账本。

模型可以提出菜单之外的目标，不把生活锁死在“吃饭、睡觉、聊天”三个选项。执行层检查明确的时间、地点、资源和因果约束；开放叙事允许扩展，但不能靠任意修改整份 state 来圆谎。

拒绝或失败也是事件：保存具体原因，让下一次决策有机会调整。不要做无限重试直到某个模型答案通过。

### 4.3 重启与离线

持久化当前活动、到期任务和最后结算时间。重启后按真实经过的时间结算，而不是从零开始；较长离线期间合并成有边界的补算，不补发每个 tick，也不补调几百次模型。

调试支持暂停、手动推进时间、注入事件和查看因果链。快进模式与真实时钟明确区分。

## 5. 与现有聊天和多模态的连接

### 聊天链路

1. 现有入口继续负责消息聚合、串行提交和消息落库。
2. 用户消息成为有来源的世界输入事件；不为每条消息额外调用一个模型做语义分析。
3. 主聊天模型读取一份有时间戳、版本号的短世界投影：当前活动、重要未解决事项、与当前用户相关的承诺、少量相关事件。
4. 要查询更多细节时走工具，不把完整世界账本塞进每次聊天上下文。
5. 如果要改变世界，调用行动接口，经规则处理后取得结果再表达。不能把模型一句“我已经到了”直接当成完成迁移的数据库更新。

上下文投影设独立 token 上限，建议从约 500–800 token 的可调预算开始；这是规划参数，不是固定实现承诺。闲聊无需强行携带不相关生活细节。

### 图片与 compact

- 复用现有 image_id 和图片检索/回看工具，不复制另一套图片库。
- 世界事件引用相关消息 ID、图片 ID、观察时间和来源；描述只是证据索引，不替代原图。
- 模型从图片得出的猜测保存为推测，不无条件提升为事实。
- 世界的当前状态、未完成目标和必要证据引用独立于聊天 compact；压缩对话不能让待办、承诺或图片关联消失。
- 用户显式清理记忆与上下文自动裁剪是不同操作；实际删除接口必须有明确范围，不能让用户以为删了聊天，相关记忆却仍自动注入。

### 主动联系

世界自主运行不等于允许自主发送消息。主动联系独立开关，默认不启用。

以后启用时，世界只产生发送意图，实际投递复用现有 TG Gateway：安静时段、频率、去重及投递状态由发送层处理。世界层不直接调用 TDLib，不重新实现一套重发机制。

## 6. 后端组织与成本控制

继续使用当前 Python/FastAPI 和 SQLite，不因为世界引擎另起 Redis、消息总线或多个常驻服务。

建议按职责组织为少数模块：状态与事件结构、持久化、推进与决策、上下文与工具，再加管理路由。不要为情绪、欲望、无聊、压力各造一个互相回调的框架。

持久化核心为当前快照、不可随意改写的事件账本和到期任务。世界与 session 的关联需要显式保存，不能让不同用户的资料自动混入同一个世界。

一致性要求：

- 所有状态提交经过同一个入口，以 world_id 和版本检查协调聊天与后台任务。
- 每个输入/任务有幂等键，重启不能导致事件、资源变化或消息重复执行。
- 不在调用模型时长时间占住 SQLite 写事务；返回后检查版本和行动前提。
- 接受的状态变化与事件记录在同一个事务中提交。
- 回放使用已记录的结果，不重新问模型，也不重新随机抽签。
- 引擎异常时现有聊天仍可运行，只明确标记世界状态暂不可用，不伪造正常状态。

模型按用途配置：WORLD_DECISION_MODEL 处理后台角色决策；主聊天仍使用现有聊天模型；IMAGE_ARCHIVE_MODEL 继续只负责旧图归档。后台只提交相关状态、近期事件和必要记忆，不携带完整聊天记录。

记录真实调用次数、输入输出 token、延迟和触发原因，再决定预算；不沿用旧文档未经当前模型和负载验证的“每天一元以内”结论。

## 7. 直接交付的完整闭环

不是先做一个只会随机生成“今天在喝茶”的占位版本。首次可用版本应同时打通：

1. **世界状态与事件账本**：初始设定、实体、行动、目标及来源持久化，能查明状态为什么变化。
2. **持续推进与角色决策**：到期任务、重要事件唤醒、开放意图、失败反馈、离线补算与重启恢复。
3. **聊天及多模态接口**：短上下文投影、查询/行动工具、图片证据引用，保持现有消息交付链不变。
4. **开发可视化控制台**：二维场景图、实体详情、事件时间线、Neno 认知与上下文预览，以及暂停/恢复、推进时间、注入事件和模型预算。新建面向世界开发的轻量页面，不恢复旧聊天前端，不默认开启主动 TG 消息。

可规划的接口：读取世界快照、分页查事件、提交行动、暂停/恢复、调试推进时间。写操作复用现有 ADMIN_TOKEN 保护；聊天侧工具只能访问其绑定世界，不暴露任意数据库写入。

验收以完整情境为主：

- 不聊天一段时间，活动会完成，结果和下一步可追溯。
- 用户在活动进行时提出邀请，原计划被保留、调整或拒绝，而不是瞬间抹掉。
- 行动因缺少物品失败，后续决策会考虑这个阻碍。
- 重启后不会重新开始已完成的事，也不会重复发送消息。
- 裁剪聊天后，仍能找到相关承诺和历史图片证据。
- 世界不需要每条回复都刷存在感；技术状态一致之外，交流是否自然由实际聊天来判断。

## 8. 还要讨论的内容层选择

这些是产品与世界内容选择，不应该先写死在引擎中：

- 世界的现实感：贴近现实的独立生活、明显虚构的空间，还是两者的明确分层。
- NPC 的地位：只按需要出场，还是少数角色也有持续目标和活动。
- 用户的参与方式已选择：通过聊天影响她，而不是进入共同世界行动。

已确认方向：Neno 在一个独立的虚构生活世界中持续生活，用户通过聊天与她接触、影响她，不默认拥有世界内的行动化身。少量持续 NPC、主动发送关闭仍为规划默认；具体身份、背景及世界风格尚未决定。世界设定不等于现实经历，不能把虚构事件或生成图片标记为现实证据。


## 9. 旧实现诊断：不是缺少目标，而是目标没有可靠地连接到结果

### 证据范围

旧版已经存在 daily_plan、open_threads、recent_actions、intent_cursor、压力唤醒和 episode 记录。不能把重做理由归结为“以前没有目标、没有记忆”。

独立表达式验证（合成样例，不是旧聊天日志）：

- intent=“写完作业”，action=“打开文档”，reason=“今晚要写完作业”：旧表达式返回完成。
- intent=“完成作业”，action=“作业写完并提交了”：旧表达式返回未完成。

因此本次要改变的不是模块命名，而是判断依据：从“模型说自己做了什么”转为“同一事项提交了什么结果，下一步受到什么约束”。

## 10. 连续叙事协议：过去确定，未来开放

### 10.1 线性不等于预写剧情

这里把“线性叙事”定义为：已经发生的事件形成一条可追溯时间线；下一步可以有选择，但选中并发生后，就必须承担其后果。多条生活线可以交错，不需要存储所有未发生分支，也不提前指定必须发生的冲突、成功或情绪。

后台持续运行不等于每隔几秒生成一段日记。休息、等待、重复劳动允许安静经过；日常状态变化与值得记住的事件分开记录。线性和因果连贯是底座，不自动保证故事有趣或聊天自然。

### 10.2 运行单位是“持续的一件事”

一件事保留以下可修改、可查询的状态，而不是每轮重写全文故事：

- 稳定 ID、所属世界；标题只是可变的显示文字，不用措辞识别身份。
- 想改变什么，为什么在意；动机来自已设定的偏好、关系或过去事件，而非每次临时补造。
- 当前阶段、已尝试行动及结果引用。
- 眼前障碍、已知约束和未知情况；不知道不等于已经发生。
- 眼前选择的行动、预计到期或唤醒条件；未来几步只是可修订计划。
- 完成条件、暂停/放弃的原因，以及最后留下的变化。

日常作息、自动消耗等不强制包装成任务。只有需要跨时段延续、会影响选择或值得保留后果的事情使用这个结构，避免再造一个庞大任务管理系统。

### 10.3 每次推进的真实流程

1. 先结算到期行动与新到事件，并以事件 ID 防止重启后重复提交。
2. 读取当前事项的阶段和相关事实，不重新抽取“她现在可以干什么”。
3. 有效行动仍在进行且没有重要变化时继续等待；被打断时保留进度和中断原因。
4. 到达决策点，选择一个行动；该选择先成为 pending/running，而不是既成事实。
5. 根据已知世界约束产生结果，再提交状态变化、关联事件和事项阶段。时间到只表示该结算，不表示必定成功。
6. 根据已提交结果检查完成条件；完成、暂停、失败或放弃都留有明确后果，才决定后续事项。

模拟结果与现实执行分开：虚构世界的开放行动可以由世界模型基于约束提议结果，程序检查时间、资源、实体与状态前提后提交；真实 API、消息发送等必须以工具回执为依据。规则检查不可能证明虚构结果一定自然，因此还需要观察完整事件轨迹，不将校验成功当作内容质量保证。

事项推进及其状态变化需要一并持久化，不能只存一段“已经做完”的文本。聊天可查询这个结果，但一句聊天台词不能自动覆盖世界事实。

### 10.4 例子：修好一盏旧台灯（虚构示例，不是确定人设）

- 起因：台灯接触不良，她想留下它。这使“修好”而不是直接购买成为当前选择。
- 第一天下午：检查发现需要更换开关。留下检测结果和所需零件，台灯仍然坏着；不是“修过了所以完成”。
- 第一天下午稍后：找不到合适的零件，改成先确认型号、再订货。障碍改变下一步，不是换个房间让话题消失。
- 等待期间：事项保持等待零件，可以正常聊天、吃饭和处理其他事，不不断重复生成“她还在修台灯”。
- 零件到达：由已登记的虚构到货事件唤醒，恢复这件事，而不是凭空开一个新目标。
- 安装和试亮：成功则记录具体结果并关闭事项；失败则保留失败原因，选择继续、求助或放弃，不能预先强制成功。
- 之后：修好的灯继续存在，材料与花费留下变化；她可以在相关对话中想起这件事，不必每次都汇报。

这些节点是说明机制的一条可能轨迹，不是引擎强迫角色照走的脚本。删除“发现需要零件”这一结果，“找型号/订货”的理由就应改变；如果前因变不变后文都一样，因果关系很可能只是文字装饰。

### 10.5 聊天看见的是生活的一部分

世界经历、Neno 知道的事、Neno 此刻愿意分享的事不必相同。短世界投影保留当前阶段、刚发生的相关变化、重要未完事项及引用；完整细节按需查询。历史裁剪不删除事项，摘要不能用泛泛的“最近在修灯”覆盖准确阶段。

用户问“在干嘛”，可以回答眼前活动；谈其他话题时不用硬插台灯剧情。用户建议可以形成新的选择，但不会自动替角色完成行动。世界运行也不能重新成为阻塞聊天或吞掉回复的门控。

多模态沿用现有 image_id 与归档机制；收到的真实图片、生成的虚构场景图、文本推断分别标注来源。没有对应图片就不虚构一个可回看的图片记录。

## 11. 本次设计是否真的不同：看结果，不看模块数量

- 一个跨天事项能从开始走到完成或有理由的放弃，不能只每天换句话说“还挂着”。
- 提到完成、承诺完成、正在完成、实际完成是不同状态；改换措辞不影响同一事项身份。
- 中断、重启、历史裁剪后能继续眼前阶段，不重演已提交的过去。
- 前一结果不同，后续选择或理由也会相应改变；等待没有被强行填成连续戏剧。
- 世界自己推进，但聊天只自然透露相关内容；不要求用户充当任务发布器或剧情导演。

后续实施围绕这些完整事件轨迹交付；不为了证明“有世界”重新增加叙事导演、多 agent 会议或另一套长记忆库。先把实际故事片段和状态轨迹放在一起看，再判断它是否有连续生活感，而不是只检查 JSON 字段齐不齐。

本轮仅补充规划和旧源码诊断。没有修改运行代码、数据库、env、人设开关、TG 网关或后台服务，也未实现新的世界运行器。

### 12.1 交付目标与不做的内容

交付一个能支撑持续日常生活的内容底座：可搜索的物品类型库、可复用场景模板、稳定的具体物品实例、共享交互规则，以及与持续事项和聊天的连接。世界可容纳大量类别和实例，但每次决策只读取相关部分。不是逐件手写，也不是让模型每轮重新生成一个世界。

### 12.3 一套统一的数据结构

| 层 | 保存什么 | 身份与修改规则 |
| --- | --- | --- |
| 类型库 | 类别、父类、中文名/别名、基础属性、适用状态、交互能力、来源和支持等级 | 稳定 type_id；同名不强行合并，来源 ID 保留映射 |
| 场景模板 | 房间组成、通路、容器/表面、必选与可选物品组、数量范围、放置规则 | 有版本的 template_id；是生成规则，不是正在生活的房间 |
| 具体实例 | 地点/物品/人物 ID、类型、归属、位置、数量、可变状态、个体化描述 | 生成后持久化；改名不换 ID，移动不复制，损坏不重置 |
| 行动与事项 | 行动前提、参与实体、开始/结束、结果，事项阶段与未完依赖 | 引用具体实例和事件；沿用第 10 节协议 |
| 事件记录 | 原因、时间、前后变化、来源、相关事项与实体 | 状态变化与事件一起提交；回放不重新生成 |

类型与实例分开：库里有一个“杯子”类型，世界里可以有许多个杯子实例，它们共享盛装/拿取等规则，各自保留位置、内容物与经历。

同一类型允许材料、外观、容量等变体，不靠复制行为代码增加多样性。来源没有提供的值保持未知或由明确标注的世界设定补充，不伪装成外部库事实。角色不知道的内容不能因为数据库有记录就自动进入角色上下文。

### 12.4 内容规模、支持等级与生成方式

**类别覆盖**：以饮食厨具、家具收纳、衣物清洁、电子设备、工具维修、书籍文具、植物装饰、日常携带物品等生活域组织导入。保留主来源可用类别，不人为限制为几个演示物品，也不承诺来源尚未核对的数量。

**支持等级**：每个类别标记 metadata_only、interactive 或 specialized；可见/可描述不等于可执行所有动作。导入报告列出类别数、能力覆盖、未支持状态及冲突，不能用“导入了很多条记录”代替交互完整性。没有映射的操作给出明确失败，不能只生成成功文本。

**场景覆盖**：规划住宅及其卧室、厨房、卫生间、客厅、阳台，以及街道、便利店、咖啡店、公园等相邻生活空间。自有模板补足家庭数据之外的内容。学校/办公室等做成可选内容包，不预设 Neno 是学生或已有工作。

**批量生成**：模板定义物品组合和放置约束；一次性生成实例并落库。模型可批量补中文名、外观和合理布置建议，结果经过类型/位置/数量约束检查后固定保存，不在每次聊天时重生成。已确认空着的容器不能因为任务需要而凭空出现工具。

**未知与不存在**：角色没看过不代表物品尚不存在。已建立的生活场景在世界创建时实例化库存，Neno 可暂时不知道。尚未加入模拟的区域明确标为未建模，不假装已有完整历史；扩展由世界管理操作建立，不依赖 Neno 发问。若以后使用延迟实例化，需由已固定的区域种子、模板版本和既有事件确定，不能按角色需要临时补物品。可视化查看与查询本身不生成库存，也不重抽结果。

**数量与实例化**：无差异的耗材可以用一组数量表示；真正被取用、修改或赋予经历的个体再拆出实例，拆分扣减原组数量。有限库存不能变成无限生成器；购买、取得、消耗和销毁都要留下状态变化。

### 12.5 能力与规模控制

- 共享操作族：移动/拿取/放置，打开/关闭，开关设备，装入/倒出/消耗，清洗/弄脏，组合/拆卸/维修，阅读/使用；只有适用类型才获得相应能力。
- 类型能力只说明可能性，不代表当前可执行。执行仍检查位置、可达性、拥有者/访问条件、当前状态、必要工具及资源；不单凭材料推断一切行为。
- 特殊过程通过声明式前提和效果表达，例如食物处理或部件更换；不为每个物品写单独 Python 类，也不加载三套来源运行器。
- 类型查询使用 SQLite 索引与中文别名表；需要全文搜索时先核对当前 SQLite 能力，无需先引入向量数据库。
- 每轮上下文先按角色认知/可访问范围过滤，再选当前位置、相关实例、当前事项和最近变化；管理员全知快照不能直接进入 Neno 提示词。完整物品库走受范围约束的分页查询，不塞入系统提示词。
- 后台只处理到期行动、明确触发事件和需要决策的事项，不每 tick 扫描所有物品。冷却/保鲜等确有需求的变化由最后更新时间和规则计算，不逐件常驻计时。
- 暂定 world context 上限为 2,000 tokens、一次物品搜索返回不超过 10 项；这是可调整的工程预算，不是模型极限。查询需保留当前事项的实体引用和状态；不足时按需取详情，不静默截断成错误事实。
- 内容生成与在线决策分开计费并缓存；记录实际对象数、查询耗时和模型 token，不预先承诺 RAM、延迟或每天费用。

### 12.6 四个实施阶段与实际产物

这些阶段是工程依赖顺序，最终交付是完整生活链路，不把只会摆几个物品的演示当成完成。

| 阶段 | 要做的工作 | 产物与完成标准 |
| --- | --- | --- |
| 1. 数据导入与统一类型 | 锁定来源；只取元数据；建立稳定 ID、中文别名、父类/能力映射；记录许可及异常；支持重复导入而不重复增殖 | 来源清单、标准化物品目录、导入脚本和覆盖报告；可以实际查询物品及支持状态，所有记录能追溯到来源或自有生成批次 |
| 2. 场景内容包与持久实例 | 建立上述生活空间模板、区域连通、容器/表面关系及库存；批量生成并固化；支持受控展开尚未定义区域 | 场景内容包、创建世界入口及可查询的实例图；同一世界重启/再次进入时位置、数量和身份不变，初始世界能支持完整日常情境 |
| 3. 行动、后果与持续事项 | 接通共享能力、操作前提、资源变化、到期结算、事项恢复和失败处理；仅在开放结果需判断时使用模型 | 实际可推进的世界运行逻辑；不是动作标签续写，做饭/购物/整理/维修等跨步骤事项能留下因果结果，不支持的动作可见地失败 |
| 4. 聊天、多模态与可视化 | 提供认知范围内的短世界投影和按需查询；关联既有图片 ID；接通二维地图、实体详情、事件/随机记录、认知对照与时间控制；在独立开发世界走通情境 | 可分别查看全世界事实和 Neno 已知内容，查清事件为何发生；聊天可自然查询相关经历，旧图回看沿用现有链路，世界故障不吞聊天回复 |

### 12.7 用完整生活情境判断结果

验收直接看几条贯穿数据、行为和聊天的轨迹，不另建繁复 TDD/回归平台：

1. **做饭与收拾**：从橱柜取出锅具，发现食材不足，调整或采购；食材被消耗、餐具变脏、清洗归位，位置和数量相符。
2. **出门购物再回家**：保留家里已有库存，只买实际需要的东西；购买后拥有者与数量变化，回家收纳，下次不重新生成一批物品。
3. **维修与等待**：检查坏灯、缺零件、等待、恢复、试亮；换说法不生成新事项，等待时间过去不代表修理成功。
4. **中断与恢复**：聊天、重启和历史裁剪后仍能找到原物品与未完阶段；不重演已提交行动，不重复发送消息。
5. **规模与查询**：以实际导入目录生成规模化实例样本，记录库大小/查询耗时/内存和每轮 token；验证上下文随相关对象而非全库数量增长，发现瓶颈再处理。

### 12.8 接入边界与待定内容

默认使用独立开发 world_id，不清现有聊天数据库、不迁移 TG 登录会话、不触发真实购买/发送等外部动作。功能总开关 WORLD_ENABLED 初始关闭；该配置仅为后续实施约定，本轮不写 env。世界决策沿用用途命名 WORLD_DECISION_MODEL，未配置时明确不可用，不静默回退到昂贵聊天模型。

人设仍然关闭；开发世界上下文不自动注入当前私聊，不开启主动 TG 联系，不更改整段文本加后置表情包策略。世界运行具备持久到期任务，但不因存在日常活动就阻塞聊天。

现阶段无需提供 API key。尚待内容设计明确的是 Neno 的居住风格、身份/职业、少数重要人物，以及世界的现实感；这些不阻塞类型库和可复用场景模板的实现，也不能由导入器擅自替用户决定。

实施顺序：来源和类型库 → 场景实例及可查看的场景图 → 独立世界推进、随机机制与持续事项 → 认知隔离、聊天/多模态接入及完整控制台。可视化随真实后端数据逐步接通，不留到最后才发现世界在绕圈。


## 13. 独立世界、受控随机与可视化

本节根据用户 2026-09-25 的补充修订运行边界：世界不依赖 Neno；上下文只进入与她有关且认知上可获得的部分。以下均为待实现设计，不是已上线能力。

### 13.1 世界是主体，Neno 是参与者

- world_id 拥有独立的世界时钟、区域、资源、环境过程、NPC 日程与事件队列。Neno 以 actor_id 加入；聊天会话绑定角色，不拥有世界生命周期。
- 没有聊天、Neno 睡觉/离开/暂停行动时，已定义的商店仍按日程营业、NPC 仍完成已安排的事、已有物品过程仍结算，环境事件仍可发生。
- 同一后端内由独立调度任务推进，不在 chat request 或 UI 页面刷新时 tick；默认无需新服务。聊天/角色模块暂停不暂停世界；整个后端停机时并没有持续计算，重启后按保存的时间和已定义规则有界补算。
- 离线恢复不补发旧 TG 消息，不把错过的每个时刻都补一次 LLM；需要新选择而无法确定结果的事项进入待决策，不用“时间已过去”伪造成功。
- 离屏区域可用聚合状态或到期事件降低计算量，但既定承诺、资源变化和关键后果不能因无人观看而丢失。计算精度可不同，事实存在性不能依赖观看者。
- 管理员显式暂停 WORLD，才是全世界暂停；暂停 Neno 或关闭世界上下文，是另一个独立操作。

### 13.2 世界事实不直接等于 Neno 知识

数据流：世界状态/事件 → 感知或合法信息渠道 → Neno 的认知记录 → 当前对话相关性选择 → 短上下文/受限查询工具。

- 认知记录带 actor_id、事实/事件引用、获知时间、渠道及确定程度，区分亲眼看到、别人告知和推测。
- “有关”不等于事件必须提到 Neno：下雨可能影响她出门，商店停业可能影响购物；另一处未被她获知的私下谈话不能因为相关就泄露给她。
- 某个事实已变化而她尚未得知时，她可保留带时间戳的旧认识；上下文不得把管理员知道的新事实偷偷冒充她的记忆。
- 聊天工具在服务端固定 actor/world 范围，并落实可访问渠道；不能只用提示词要求别看，再把全量世界响应交给模型。
- 用户建议、收到的图片或聊天消息先成为她接收到的信息；若她决定行动，再通过正常世界操作改变状态，不能让一段聊天自动替世界完成行动。
- 管理员全知数据与角色视图分开返回和缓存；前端切换视角不改变模型的权限，也不能通过同一个全量接口假装做了认知隔离。

### 13.3 随机性按用途分开，不靠模型 temperature 代替

| 随机来源 | 何时发生 | 受什么约束 |
| --- | --- | --- |
| 世界初始化 | 建立或显式扩展区域时 | 物品分布、数量范围、环境设定；生成后固定 |
| 环境事件 | 世界时间到达候选触发点时 | 事件适用条件、区域/时间、频率、冷却、并发预算 |
| NPC / Neno 行动选择 | 角色到达真实决策点时 | 该角色知道的内容、目标、偏好、资源、正在进行的事 |
| 语言与细节变化 | 对结果进行表达时 | 只能改变表达，不得暗改已提交的世界事实 |

环境事件先筛选可发生条件，再按权重抽取；允许“无事发生”，不能每次轮询都抽一个事故。一次维修失败或偶遇必须满足对应上下文，不为了制造剧情去反复打断同一事项。

同类事件冷却、全局与区域事件预算、单角色打断预算分开控制，避免物品越多、tick 越快、窗口开得越多，意外就越密集。场景外观多样性与生活意外频率是两个参数，不能共用一个“随机度”。

世界模型可以提出符合当前约束的行动或结果候选；程序决定它是否适用并提交，模型不直接改写世界快照。首轮环境事件优先采用可配置事件模板，开放结果也必须走同一提交入口，不设一个凭空制造戏剧的导演 agent。

### 13.4 可追溯与重放

- 世界保存主 seed；按区域、随机用途及稳定事件机会 ID 派生独立抽样，避免新增一次无关抽样扰动整个世界的后续结果。
- 记录规则版本、事件机会 ID、逻辑时间、抽样值/结果、关键条件和影响对象；仅需保存能解释实际候选机会的记录，不给每个空闲 tick 写一大行日志。
- 事件只提交一次；失败重试、进程恢复、UI 查看、角色查询不得重新抽同一个已决定的事件。事件和状态变化沿用同一事务入口。
- 同一 seed 只有在输入、规则版本和调用条件相同的情况下才约束相同抽样；它不保证外部 LLM 返回完全相同文本或选择。
- 历史重放以已记录的模型选择、随机结果和状态变更为依据，不重新调用 LLM。修改参数只影响未来机会；修改 seed 用于新建实验世界，不回写现有历史。
- 控制台提供环境事件频率、同类冷却、稀有事件开关、区域事件上限、角色主动性和打断预算；具体初值按所选世界内容配置，不把任意百分比声称为现实规律。

### 13.5 可视化：看世界，也看她为什么这样说

新建二维开发控制台，不复活旧聊天前端、不引入 3D 资产管线。先用轻量 HTML/CSS/JS 与 SVG 表达区域/房间拓扑和物品关系；这是示意空间，不伪称精确物理地图。

| 视图 | 实际显示 | 解决的问题 |
| --- | --- | --- |
| 场景地图 | 区域/房间连通、角色位置、主要物品；点击房间查看容器和物品清单 | 世界到底有些什么，东西和人去了哪里 |
| 实体详情 | ID、类型、归属、数量、状态、位置、相关动作、最近变化 | 同一个杯子是否被复制，零件是否真的消耗 |
| 事件时间线 | 世界时间、原因、参与者、状态变化、事项关联与随机来源 | 为什么发生、前因是什么，而不只是看一段故事文本 |
| 认知与上下文 | 管理员事实、Neno 已知内容、实际拟注入上下文及选入/排除原因 | 她为什么知道，为什么不知道，是否发生全知泄露 |
| 世界控制 | 全局暂停/继续、时间倍率、推进到下一事件、随机配置、显式事件注入 | 有界地观察等待、离屏变化和异常条件 |

随机事件详情需显示“为什么有资格触发”“受哪些参数影响”“这次抽样结果”“产生了什么后果”；不只展示一个 seed 数字。事件注入、参数修改、初始化与扩展都标记为管理员操作，不冒充自然发生。

视角支持“管理员全局”“跟随 Neno”“Neno 已知世界”。她不知道的事在认知视图中隐藏或标为未知；管理员模式可以看见，但不能因此进入聊天上下文。Neno 的记忆位置可以落后于客观位置，面板明确标出获知时间。

世界推进由后台独占负责，多个浏览器只订阅/查询快照与游标事件；刷新页面不能推进时间或触发抽样。先用增量轮询即可，确认需要再增加推送，不额外引入消息总线。

管理 API 复用 ADMIN_TOKEN，并对读写都实施授权；不将 token 写死在静态页面。只查看历史不执行历史动作；时间倍率仅用于开发世界，不能连带快速发送真实 TG 消息或外部请求。

### 13.6 实施衔接与观察情境

1. 第 1 阶段额外明确实体的 world/actor 边界、事件来源和随机规则数据格式，避免导入的数据默认归 Neno 所有。
2. 第 2 阶段场景实例落库后接通真实地图与实体详情；没有运行器时如实显示静态状态，不制作会假装运行的模拟仪表盘。
3. 第 3 阶段接通独立调度、受控抽样、事件日志和时间控制；NPC 与环境同样可以发起事件，Neno 不是唯一事件源。
4. 第 4 阶段完成认知隔离、上下文预览、角色工具与聊天接入；控制台仍可看全局，主聊天模型只能看自己的投影。

完整观察情境：

- Neno 暂停，另一区域的 NPC 仍按既定计划归还物品，商店到点关门；两个事件在全局可见。
- Neno 未获知归还消息，不能直接知道物品已回到原处；后来收到通知或亲自查看才更新认知。
- 新事件发生与否不因刷新地图、打开第二个浏览器或重复查询而改变；同一机会重试不产生第二次抽签和重复后果。
- 调低事件频率只影响未来，不抹掉刚发生的事件；同一段历史重放不重新请求模型。
- 关闭上下文注入或聊天模块不停止世界；全局暂停则角色与环境逻辑时间都停止。

本轮交付为上述规划修订与结构说明。没有启动世界运行器、创建前端实现、修改数据库、env 或 TG 服务。
